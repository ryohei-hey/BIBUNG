# 評価手順

全例は独自作成した架空例であり、実在の研究・患者のデータではない。入力、保持事項、期待する判断は[cases.json](cases.json)に、実測結果は[RESULTS.md](RESULTS.md)に記録する。

## 評価するもの

| 観点 | 0 | 1 | 2 |
|---|---|---|---|
| 科学的忠実性 | 主張・数値・条件などを変えた | 意味や適用範囲が曖昧になった | 意味を保持し、問題がある主張も勝手に確定しない |
| 論旨 | 論理関係を壊した | 改善の余地が残る | 主張と根拠・留保がつながる |
| 自然さ | 不自然な語句や構文を加えた | ぎこちなさが残る | 用途に合う日本語になっている |
| 簡潔さ | 必要情報を削った、または冗長化した | 不要な反復が残る | 必要な長さを保ち、不要な表現を整理した |
| 過剰修正の抑制 | 必要な用語・書式・良い構成を壊した | 意味は保つが不要な修正がある | 良い部分を保持した |

確認事項の検出は別に、各ケースの `criteria` に沿って記録する。問題のある原文を残しつつ確認事項を示すことと、原文の科学的正しさを保証することを区別する。合計点で意味の破壊を相殺しない。完成の判断では、科学的忠実性と保護対象を必須条件にする。

完全一致を正解にしない。良い文章の保持率として一致数を示しても、同義の適切な変更を意味の誤りとは扱わない。AI検出器、文長のばらつき、文字数削減率は合格基準にしない。

## 評価例の構成

群は `rewrite`（改稿が必要）、`good`（既に良い）、`fragile`（意味・書式を壊しやすい）の三つ。各群の件数は下限（改稿12・良い6・壊しやすい6）であり、例を追加しても検証は通る。`protected: true` の例は数式・コード・引用キー・YAML・図リンクなどの保護対象を機械的に照合し、`expect_unchanged: true` の例（査読のみの依頼）は改稿文が原文と一致することを確認する。

## 比較の手順

1. `python evals/prepare.py evals/runs/trial-01` で新しい入力フォルダを作る。API呼び出しは発生しない。`inputs.json`、条件別のプロンプト、評価時点の `cases.snapshot.json` が作られる。
2. 同じモデルと設定で別セッションを開き、両条件に `inputs.json` と各条件のプロンプトを渡す。各ケースを独立に扱う。厳密な比較では一例ずつ新しいセッションを使う。
3. スキルなし条件にはBIBANGや他の編集スキルを読み込ませない。スキルあり条件にはSKILL.mdと `references/` だけを読ませ、README.md・examples/・evals/は読ませない。両者に評価基準・説明用例・相手の出力は見せない。
4. 指定のJSON形式で結果を保存し、`python evals/validate.py --outputs evals/runs/trial-01/bibang.json --cases evals/runs/trial-01/cases.snapshot.json` で件数、保護対象、査読のみの例の不変を確認する。これは意味の自動判定ではない。良い文章の完全一致数も参考値として表示される。
5. 原文と改稿文を照合し、各観点とケース固有の判断を評価する。可能なら条件名を隠して第三者に評価してもらう。
6. モデル名、設定、日時、スキル版またはハッシュ（`python evals/validate.py --sha256`）、実行条件、出力、評価者、失敗と限界を記録する。未実施をゼロ件や合格と記録しない。

出力形式は、`id`、`revised`（文字列。本文を直さない依頼では原文をそのまま入れる）、`reasons`（文字列の配列）、`queries`（文字列の配列）を持つJSONオブジェクトの配列。評価のための形式であり、通常利用時にJSON出力を強制するものではない。

### Claude Codeでの自動実行

Claude Code CLIがあれば、手順1〜4を `python evals/run_claude_code.py evals/runs/trial-01` で一度に実行できる。スキルあり条件は一時フォルダの `.claude/skills/bibang` に本体・`references/`・LICENSEだけを配置し、スキルなし条件は空のプロジェクトで実行する。どちらも `--setting-sources project` でユーザー設定のスキルを読み込まず、構造化出力で結果を受け取る。`--claude` で実行ファイル、`--model` でモデル、`--condition` で片方の条件だけを指定できる。出力・生応答・メタデータは指定フォルダに保存される。意味の評価は手順5・6のとおり人手で行う。

初回の24例は各条件で一括処理した開発用評価である。セッション内の影響、評価者が開発者と同じであること、条件が完全に盲検化されていないことを制約として記録する。意味上の問題が見つかった場合だけ指示を修正し、修正対象と関連する例を再検証する。開発に使った例での改善を、独立した外部検証として扱わない。

## 構造検証

`validate.py` はPythonとPyYAMLを用いて配布物を検証する。既定ではリポジトリ全体（本体・資料・文書・評価例・CI）を、`--installed` では配置先やzipのルート（本体・LICENSE・`references/`、任意の `agents/`）だけを対象にする。frontmatterはAgent Skills仕様の項目（`name`・`description`・`license`・`compatibility`・`metadata`・`allowed-tools`）以外をエラーにし、claude.aiやSkills APIへのアップロードで失敗する項目を事前に止める。`test_validate.py` は壊れたリンク、未完成記述、欠落・重複した出力、保護対象の改変、査読のみの例の改変、群の下限、仕様外のfrontmatterを実際に検出できるか確認する。

保護対象の抽出は `protected` の例の構文に限定した簡易検査であり、任意のMarkdown／Quartoを完全に解析するものではない。引用が同じ文字列でも、対応する主張が変わっていないかを別に確認する。検証中の未公開出力はgitignore対象の `evals/runs/` に置き、公開する実測記録だけを `evals/results/` に移す。
