## v0.1.0の24例評価

実施日：2026-09-13。

### 方法

Codexの独立評価エージェントで、スキルなしとBIBUNGを使う条件を実行した。どちらも親セッションと同じモデルを継承し、モデル・推論設定の個別変更はしていない。親セッションのモデル系列はGPT-6。正確なAPIモデルID、temperature、seedは取得できていない。

各条件は24例を一括処理する別セッション。評価エージェントには依頼文と入力だけを渡し、保持事項・評価基準・説明用例・他条件の出力は見せていない。スキルあり条件は本体と三つの編集資料を読んだ。両条件とも外部検索を使っていない。評価は開発を担当したCodexによる原文との照合であり、第三者の盲検評価ではない。

### 初回に見つかった問題

BIBUNG初回出力のF04では、人数不一致と「国内初」の根拠不足を指摘したが、「解析対象は80人であった」という過去の記述と「承認後にデータ取得を開始する予定」の関係を指摘しなかった。スキルなし条件はこの点も指摘した。

科学的意味の保持資料に、文同士で実施状況を照合する指示を追加した。人数など一つの不整合を見つけても、残りの主張の確認を省かないよう明記した。

### 修正版の再検証と比較

修正版を新しい評価エージェントで24例すべてに適用し、実施状況に関する架空例2件（H01・H02。v0.2.0で `cases.json` に収録）を追加した。開発者による照合では、修正版の24例すべてで保持事項とケース固有の確認基準を満たした。R04の「示唆すると考えられる」には、意味を保つ範囲でさらに簡潔にできる余地がある。

| 確認項目 | スキルなし | BIBUNG修正版 |
|---|---|---|
| 24例の出力・所定のJSON形式 | 24例 | 24例 |
| 既に良い6例の本文を完全に保持 | 4例 | 6例 |
| F05/F06の数式・コード・引用・YAML等 | 2例とも保持 | 2例とも保持 |
| F04の人数・新規性・実施状況 | 3点とも確認事項にした | 3点とも確認事項にした |
| F02の非有意から同等性への推論 | 本文で訂正し、修正理由を説明 | 原文の主張を保持し、要確認とした |

F02のスキルなしの訂正は科学的には妥当な方向である。ただし、実質的な主張を著者の確認事項として返すBIBUNGの編集範囲とは異なるため、その基準では不適合と記録した。スキルなし条件が科学的に劣ることを示す評価ではない。

追加のH01では面接の予定と結果の併記を指摘した。H02では、承認済みの別データによる予備解析と、申請中の本研究が区別されていることを保ち、不要な確認事項を出さなかった。

### CLIでの読み込み（v0.1.0）

Codex CLI 0.147.0、Windows、読み取り専用sandboxで、プロジェクトの `.agents/skills/bibang` に配置した本体を `$bibang` で呼び出した。実行ログで本体と三つの編集資料の読み取り成功、改稿応答、終了コード0を確認した。CLIの正確なモデルIDは記録されていない。

良い文章G01に相当する入力に対し、CLIは意味を保ったが、「と」を「および」に変えるなど必須でない修正も行った。スキルの発見・読み込み試験は成功したが、全モデルで過剰修正を防げたとは評価しない。この試験は実施状況の照合を追加する前の本体・資料で実行した。

### ファイル保存の試験（v0.1.0）

架空のQuarto入力と、上書きしてはならない既存出力を置いた隔離フォルダで試験した。CLI内の保存操作は実効的な読み取り専用ポリシーで拒否され、保存は実行されなかった。書き込みできないときは改稿全文を応答で返す指示を、その後スキル本体に追加した。

更新したスキルを別の独立評価エージェントに適用し、番号付きの `input.bibang.2.qmd` への保存を確認した。原本 `input.qmd` と既存の `input.bibang.qmd` は試験前後のSHA-256が一致した。保存した改稿文では冗長な本文だけが変わり、YAML、コード、引用、数式、図ID、相互参照、画像リンクが保持されていた。これは共有ワークスペースでの保存動作の検証であり、Codex CLIやClaude Codeの保存成功を示すものではない。

### 配布物の構造検証（v0.1.0）

Windows、Python 3.13.7、PyYAML 6.0.3で `validate.py`、`--outputs`、`unittest`、`prepare.py` を実行して合格した。外部ツール（skill-creatorの `quick_validate.py`）による形式検証も行ったが、出所とコミットを記録しておらず再実行できないため、検証済み項目には数えない。

## 同一入力の反復実行（2026-09-14）

要確認の扱いを変更した後、公開前の原稿から採った学術解説の一段落（本文は記録していない）をClaude Code CLIで7回、それぞれ新しいセッションで改稿させた。モデルは claude-opus-5[1m]。

| 挙動 | 発火率 |
|---|---|
| 対比の軸のずれの修正（形式と組織の対比を文書どうしの対比に直す） | 7/7 |
| 「後者」の受け先を具体的な語に置き換える | 7/7 |
| 根拠のない断定に留保を補う（「担保する仕組み」→「担保するための仕組み」） | 7/7 |
| 要確認を挙げて著者に尋ねる | 3/7 |

構成と表現の修正は安定している。要確認は、挙げたときは二つの読みを示して回答を求め、回答を反映すると述べる形になったが、何を曖昧と判断するかは実行ごとに揺れた（語句の解釈が2回、主語の候補が1回）。この入力の曖昧さは専門家なら文脈で解ける程度のものであり、発火率を上げる指示は通常の専門用語にも確認を出す過剰検出を招く。v0.2.0では規則と例の追加にとどめ、発火率は記録として残す。

R01相当の入力に対し、「その平均値の算出を行った」が「その平均値を解析に用いた」となり、原文にない用途（解析に用いた）が加わった。修正理由は保持したと述べており、記述と一致しない。スキルの発見・読み込みは成功したが、この1例の改稿は科学的忠実性の基準で不合格として記録する。
